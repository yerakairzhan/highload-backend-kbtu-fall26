# SIS #2 — Protocol implementation: gRPC vs REST/JSON

The blog API designed in [SIS #1](../../tree/sis-1) — accounts, profiles, posts, comments, likes and
image uploads — implemented in Go over **gRPC (protobuf over HTTP/2)**, the protocol SIS #1 chose for
service traffic, with **idempotency, timeouts and retries**, and measured for **latency and payload
size** against a **REST/JSON baseline**. Results: **[REPORT.md](REPORT.md)**.

> **Deviation from the task text:** the task says Java; this repository implements every week in Go
> (see the course index on `main`). Nothing measured here depends on the language: both protocols
> run the same Go handlers.

## One handler, two protocols

The services use [Connect-Go](https://connectrpc.com): one generated handler answers both protocols
on the same path, so the comparison changes only the protocol, never the business code.

| Target | Protocol | Encoding | HTTP | Request |
|---|---|---|---|---|
| `grpc` | gRPC | protobuf | HTTP/2 (cleartext) | `POST /api/v2/blog.PostService/GetPost`, `application/grpc` |
| `json_h1` | Connect | JSON | HTTP/1.1 | same path, `application/json` — **the REST/JSON baseline** |

The baseline sends JSON in a POST to an RPC-style path instead of `GET /v1/posts/{id}`; only the path
string differs, not the encoding, the framing or the headers.

## Layout

```
proto_schema/            API contract (proto2): entity file + service file per domain
internal/pb/             generated by `buf generate` (not committed)
internal/backend/
  handler/               Connect handlers, registered with the interceptors
  interceptor/           auth (verifies the JWT), server timeout cap
  security/              JWT issue / verify
  service/               auth, users, posts, comments: idempotent creates, optimistic lock, seed data
  platform/              HTTP server: HTTP/1.1 and cleartext HTTP/2 on one port
internal/cloud/storage/  S3-compatible object storage: presigned image uploads
internal/repository/     repositories (mo.Result) over an in-memory store; Snowflake ids
internal/client/         client side: transports, retry interceptor, gRPC / JSON clients
internal/loadgen/        open-loop benchmark, payload sizes, report
internal/common/         config (YAML + CONFIG_FILE), errs, log
cmd/blog_platform/       the server
cmd/loadgen/             the measurement tool
```

Rows are kept in memory on purpose: the benchmark compares protocols, so storage must cost the same
for both. SIS #3 replaces it with PostgreSQL behind the same repositories. Images go to an
S3-compatible object store ([RustFS](https://github.com/rustfs/rustfs) in Docker; MinIO no longer
publishes container images).

## Accounts, profiles, uploads

| RPC | What it does |
|---|---|
| `AuthService.Register`, `Login` | bcrypt password hash; returns a **15-minute HS256 JWT** access token and an opaque **refresh token** (only its SHA-256 is stored). An unknown username costs the same bcrypt comparison as a wrong password, so timing does not reveal which usernames exist. |
| `AuthService.RefreshToken` | Each refresh token works **once** and returns a new pair. Presenting one that was already used means it was copied: the whole login is revoked. |
| `UserService.GetMe`, `GetUser`, `UpdateProfile` | Profiles (username, display name, bio). Posts and comments store the author name at write time (SIS #1). |
| `PostService.GetUploadUrl` | A **presigned POST policy**: the client uploads the image straight to the object store, which itself rejects another content type, a file over 5 MB or another key. (A presigned PUT only signs the host, so it would accept anything into a public bucket.) |

Every request may carry `Authorization: Bearer <access token>`; the auth interceptor verifies
signature, algorithm (HS256 only), issuer and expiry. No token = anonymous: reads work, writes return
`unauthenticated`. A token that does not verify is rejected, not ignored.

## Idempotency, timeouts, retries

| Mechanism | Where | What it does |
|---|---|---|
| Idempotency key | [`post_service.go`](internal/backend/service/post_service.go), [`comment_service.go`](internal/backend/service/comment_service.go) | `CreatePost` / `CreateComment` store `(user_id, idempotency_key) → id` in the same transaction as the insert. A retry returns the first result; the same key with another payload is rejected. |
| Idempotent by design | `LikePost`, `UnlikePost`, `DeletePost`, `DeleteComment` | Keyed by `(post_id, user_id)` or a soft delete: doing it twice changes nothing. |
| Retry safety in the schema | [`post_service.proto`](proto_schema/post_service.proto) | `idempotency_level` marks reads and idempotent calls; the client reads it from the generated code. |
| Client retries | [`retry_interceptor.go`](internal/client/retry_interceptor.go) | Retries `UNAVAILABLE` / `DEADLINE_EXCEEDED` on retry-safe calls only (a create needs a key), bounded attempts, exponential backoff with full jitter. |
| Client deadline | same | Per-attempt timeout, sent to the server (`grpc-timeout` / `Connect-Timeout-Ms`), so the server stops when the client stops waiting. |
| Server timeout | [`timeout_interceptor.go`](internal/backend/interceptor/timeout_interceptor.go) | Caps every RPC at 2 s whatever the client asked for. |

Proved by [`handlers_test.go`](internal/backend/handler/handlers_test.go), over both protocols:
a create whose response is lost after commit is retried 3 times and stores **one** row; a create
without a key is not retried; a 50 ms per-attempt deadline returns long before a 500 ms stall; a
bad token is rejected. Auth, refresh rotation, profiles and uploads have their own tests in
[`service/`](internal/backend/service) and [`security/`](internal/backend/security).

## Run it

Prerequisites: Docker Desktop (Compose v2). For local builds and tests: Go 1.26+ and the tools in
[`tools.txt`](tools.txt) (`make install-deps`).

```bash
docker compose up -d --build
```

Over JSON (the baseline). The server seeds 100 users, `user_0001` … `user_0100`, password
`lab-password` (lab only):

```bash
curl -s -X POST localhost:8080/api/v2/blog.AuthService/Login -H 'Content-Type: application/json' -d '{"username":"user_0001","password":"lab-password"}'
```

```bash
curl -s -X POST localhost:8080/api/v2/blog.UserService/GetMe -H 'Content-Type: application/json' -H 'Authorization: Bearer <access_token>' -d '{}'
```

All measurements (~10 min; keep the machine awake) — `results/*.json` and `results/summary.md`.
Every benchmark request is authenticated, as a signed-in app's requests are (10 seeded users'
tokens):

```bash
./run-all.sh
```

Tests:

```bash
make test
```
